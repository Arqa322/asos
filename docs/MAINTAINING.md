## 1. Порядок работы

1. Отдельная ветка на каждое изменение: `git switch -c fix/zapret-strategy`.
2. Меняете файлы (см. таблицу ниже). Сгенерированные файлы руками не правите — правите источник и запускаете генератор.
3. Запускаете проверки (раздел 9). Всё, что можно проверить без сборки ISO, проверяется за пару минут.
4. Обновляете `CHANGELOG.md` (всегда) и `README.md` (если поменялось то, что видит пользователь).
5. Коммит с понятным сообщением в повелительном наклонении: «Add Wi-Fi menu to huilo-menu», «Fix zapret restart on resume».
   Одна логическая правка — один коммит.
6. `git push`, смотрите CI (GitHub → Actions). Красная задача — читаете лог, чините, пушите снова.
7. Слияние в основную ветку через pull request. **Историю опубликованных веток не переписываем** (`push --force` только
   по общей договорённости).
8. Релиз — тег `vГГГГ.ММ` (например `v2026.12`): CI соберёт ISO и опубликует релиз.

## 3. Оформление (тема)

Единственный источник цветов — `theme/palette.toml`:

```toml
[colors]
ink1  = "#11141b"   # фон окон и терминала
amber = "#f2a33a"   # главный акцент
```

Шаблоны в `theme/templates/` повторяют структуру `archiso/`: `theme/templates/airootfs/etc/skel/.config/waybar/style.css`
превращается в `archiso/airootfs/etc/skel/.config/waybar/style.css`. В шаблоне вместо цвета пишется имя:

| В шаблоне | Получится | Где удобно |
|---|---|---|
| `@{amber}` | `#f2a33a` | CSS, rasi, toml, kitty |
| `@{amber.hex}` | `f2a33a` | Hyprland/hyprlock: `rgba(@{amber.hex}ee)` |
| `@{amber.rgb}` | `242, 163, 58` | CSS с прозрачностью: `rgba(@{amber.rgb}, 0.6)` |
| `@{amber.argb}` | `#fff2a33a` | Qt (qt6ct) |
| `@{amber.float}` | `0.949, 0.639, 0.227` | Plymouth |
| `@{font.ui}` | `Inter` | шрифты |

Правила:

* Сгенерированный файл начинается со строки `generated from theme/templates …` — **не правьте его в репозитории**,
  иначе следующий запуск `make-theme.py` затрёт правку, а CI упадёт на `make-theme.py --check`.
* Новый файл с цветами → кладёте шаблон в `theme/templates/<путь как в archiso>` и запускаете генератор.
  Генератор сам допишет заголовок-комментарий подходящего вида (`#`, `//`, `--`, `/* */`).
* Пользователь на своём компьютере может свободно править свои `~/.config/...` — `huilo-update` сохранит копию.
* Тёмные фоны — `ink0…ink4`, текст — `mist/fog/snow`, акцент — `amber`; новые цвета добавляйте в палитру,
  а не «зашивайте» в шаблон.

## 4. Пакеты и группы

`archiso/packages.x86_64` разбит на блоки:

```
# ---------- Hyprland desktop ----------          ← без тега: всегда в образе
# ---------- [games] Atom game pack ----------     ← тег: необязательная группа
```

* Новый пакет — в подходящий блок, одна строка, комментарий `#` можно оставить рядом.
* Новая необязательная группа: блок с тегом `[имя]` + описание и порядок в `DESC`/`ORDER` в `scripts/pkg-select.sh`.
* Проверка: `python3 scripts/check-packages.py` — пакет существует, зависимости разрешаются, нет конфликтов файлов,
  а «виртуальные» зависимости не тянут случайный пакет (список разрешённых — `ALLOWED_AUTO`).
* Если пакет нужен и уже установленным системам — добавьте его в `pkgs=(...)` в `scripts/update-installed.sh`.

## 5. Новая команда huilo-*

1. `archiso/airootfs/usr/local/bin/huilo-что-то`, первая строка `#!/usr/bin/env bash`, в шапке — описание и примеры
   (её же печатает `--help`: `sed -n '2,15p' "$0"`).
2. `set -uo pipefail` (или `-euo` для скриптов, которые должны падать при первой ошибке). Осторожно с `set -e`:
   последняя строка функции вида `[[ … ]] && cmd` возвращает ошибку — пишите `if`.
3. В `archiso/profiledef.sh` → `file_permissions` строка `["/usr/local/bin/huilo-что-то"]="0:0:755"`
   (иначе в ISO файл потеряет право на запуск; `scripts/check-permissions.sh` это поймает).
4. Ярлык в меню приложений — `airootfs/usr/share/applications/huilo-…desktop`; пункт в `huilo-menu hub` — по желанию.
5. Горячая клавиша — `hyprland.lua` **и** `usr/share/huilo/sway/config` (шаблон в `theme/templates/…`), HOTKEYS.txt, README.

## 6. Конфиги рабочего стола и обновление установленных систем

Файлы в `etc/skel/` получает только **новый** пользователь. Чтобы изменение дошло до тех, у кого Huilo уже
установлен, его разносит `scripts/update-installed.sh` (команда `huilo-update`). В нём два списка:

```bash
MANAGED=(...)   # файлы Huilo: заменяются; если пользователь их менял — копия <файл>.bak-<дата>
SEEDED=(...)    # личные файлы: создаются, только если их нет (hypr/user.lua, kitty/user.conf, huilo/sway.conf)
```

* Добавили новый конфиг в `etc/skel` → допишите его в `MANAGED` (или в `SEEDED`, если это заготовка для пользователя).
* Личные настройки пользователя должны жить в отдельных файлах, которые мы **никогда** не перезаписываем:
  `~/.config/hypr/user.lua`, `~/.config/kitty/user.conf`, `~/.config/huilo/*.conf`. Основной конфиг их подключает.
* Системные файлы (`/usr/local/bin`, `/usr/share/huilo`, службы) копируются целиком в разделе «system files».
* Скрипт должен быть **идемпотентным**: второй запуск подряд ничего не ломает и не плодит лишних копий.

## 7. Legacy: как менять, ничего не ломая

«Legacy» — всё, на что уже кто-то опирается: имена команд, ключи настроек, пути, горячие клавиши, параметры ядра.
Правила Huilo:

1. **Переименование команды** — старое имя продолжает работать минимум два релиза.
   * строка в `archiso/airootfs/usr/share/huilo/legacy.map`: `старое  новая команда  с-какой-версии  удалить-после`;
   * симлинк на `huilo-legacy`: в `usr/local/bin/` (если старое имя вызывается из старых конфигов) или в
     `usr/local/lib/huilo/legacy/` (этот каталог в конце `PATH`, ничего не перекрывает);
   * `huilo-legacy` выведет в терминал «… переименована в …» и запустит новую команду с теми же аргументами;
     в журнал пишется `huilo-legacy: old command … used` — видно, пользуется ли кто-то старым именем.
   * Пример: `huilo-power` → `huilo-menu power`, все `asos-*` → `huilo-*`. Список: `huilo-legacy --list`.
2. **Переименование настройки / переменной** — новая читается первой, старая — как запасной вариант
   (пример: `HUILO_WITHOUT`, но `ASOS_WITHOUT` тоже работает).
3. **Перенос файлов и путей** — миграция в `update-installed.sh` в блоке «один раз», с проверкой «есть старое и нет
   нового» (пример: `/etc/zapret/asos.conf` → `huilo.conf`, `~/.config/asos` → `~/.config/huilo`). Данные пользователя
   переносятся, а не удаляются.
4. **Замена программы** (например wofi/mako → rofi/swaync) — старые конфиги пользователя не удаляются, а
   переименовываются в `*.bak-<дата>`; скрипты умеют работать и без новой программы (fallback), пока она не установлена.
5. **Горячие клавиши** не переназначаем на другие действия; новая функция — новая комбинация.
6. **Удаление** — сначала пометка в CHANGELOG в разделе «Deprecated» с датой, удаление — не раньше даты из `legacy.map`,
   с записью в «Removed».
7. **История git** опубликованных веток не переписывается; откат — новым коммитом (`git revert`).

## 8. README и CHANGELOG

**CHANGELOG.md** — обновляется в каждом изменении, в разделе `## [Unreleased]`, по группам
(формат [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/)):

```markdown
## [Unreleased]
### Added       новое
### Changed     изменилось поведение или вид
### Deprecated  будет удалено (когда и чем заменить)
### Removed     удалено
### Fixed       исправлено
```

При релизе `[Unreleased]` переименовывается в `[2026.12] - 2026-12-15` и создаётся тег `v2026.12`.

**README.md** — для пользователя, а не для разработчика. Обновляйте, когда меняется то, что человек видит или набирает:

| Изменили | Раздел README |
|---|---|
| программы в образе | таблица в начале, «Установка без лишних программ» (группы) |
| горячие клавиши | «Live-режим», «Оформление и меню» (+ `HOTKEYS.txt`) |
| команду `huilo-*` | раздел этой команды; новая команда — новый короткий раздел с примерами |
| структуру репозитория | «Структура репозитория» (+ `docs/ARCHITECTURE.md`) |
| сборку / установку / обновление | «Сборка», «Установка на диск», «Обновление уже установленной системы» |

Правила текста: по-русски, коротко, сначала *что это даёт*, потом команда. Команды — в блоках ```` ```bash ````,
клавиши — `SUPER+D`. Не дублируйте в README то, что подробно описано в `docs/` — дайте ссылку.

## 9. Проверки перед push

```bash
bash -n build.sh scripts/*.sh archiso/airootfs/usr/local/bin/*   # синтаксис всех скриптов
scripts/check-permissions.sh                                        # права исполняемых файлов в ISO
python3 scripts/make-theme.py --check                               # тема собрана из палитры
python3 scripts/check-packages.py                                   # пакеты есть в Arch, зависимости сходятся
python3 scripts/check-hyprland-config.py                            # hyprland.lua против API Hyprland (нужен lua5.4)
scripts/tests/test-huilo-ai.sh                                      # ИИ-помощник против фальшивого сервера
scripts/pkg-select.sh --list-groups                                 # группы пакетов читаются
```

Остальное (настоящий Hyprland, rofi, waybar, swaync, сборка ISO) проверит CI. Полную сборку локально:
`sudo ./build.sh` на Arch или `./build.sh --docker` где угодно (нужно ~40 ГБ свободного места).
